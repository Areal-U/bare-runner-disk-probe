# Bare Personal ARM64　次回ビルドの準備版

Bare成果担当はこの枝で入力と受領を点検し、後日の本番反映用の差分を選ぶ。本番基点は `f3ed4479912a30959859d81328af3fd4dc6d8d00`。試験枝へのpushで起動するworkflowはない。

## 次回の開始手順

1. 同じ版を続ける場合は、元の本人向け成果、登録、初回runと現在のattempt、受領済みの最新の親を照合する。完成品があれば再利用し、転送失敗なら既存回収を使う。成果担当が参照する実コマンド・有限な復旧分岐は [入力と親の判定](next_build/INPUTS.md) にある。
2. 上流更新を選んだ場合は、指定したBareコミットが要求するChromiumを固定する。`next_build/render_input_assertions.py` で版名・版コード・パッチ数・同居GN・APK検査に対応する差分を隔離ディレクトリへ出す。更新判断は版ごとに行う。新しい生成グラフで終盤ラベル、変更したOS依存とパッチを確認する。旧版の生成物は無条件には読み込まない。
3. 現版で共通に採るファイルは [本番反映候補の一覧](next_build/product-paths.txt) に固定した。通常入口は `.github/workflows/bare-checkpoint-transfer.yml`。12区間・消失復旧の呼出しから `bare-r28-native-slot.yml`、`bare-arm64-probe.yml` を経て計算と圧縮へ至る。旧キャンペーンは旧HEAD・親・本人宛先に拘束される。新しい本番では成果担当と既存回収担当が実際の対象HEAD、親、本人宛先、期限、空き容量の登録と応答を用意する。再開にあたってR28の古い受付を新規起動に転用しない。同版・同じS2・同じ本人宛先なら、成果担当が `next_build/render_campaign.py` で新しい名前に固定した登録と復旧の差分と未発行フォームを生成できる。
4. 次のGitHub実地比較は下表の条件で選ぶ。ホスト測定が未完でも、標準方式のまま次回用候補を準備できる。実運用への反映・起動は別途決定する。

この枝の先頭をチェックアウトした状態で、一覧にある共通差分だけを再生成できる。実際の本番枝に別変更があれば適用先を保護して再照合する。

```bash
base=f3ed4479912a30959859d81328af3fd4dc6d8d00
mapfile -t paths < next_build/product-paths.txt
git diff --binary "$base" HEAD -- "${paths[@]}" > ../bare-next-common.patch
```

## 標準として選んだ設定

* 通常は1台・2並列。締切は計算側の終了処理60分、受取側35分。区間末で保存し受領後に次へ進む。受取役は同時起動。既存親の回収・再利用と新しい計算を区別する。
* 走査は通常30秒、上限接近や終盤5秒、軽量な空き・inode点検0.5秒。修正版は通常のC++を終盤と誤認せず、子が終了した時点で走査中だった1件も集計する。
* 通常入力 `checkpoint_compression=auto` は、静止した木の見かけサイズが実測世代の生tar 9,630,842,880 B以下ならzstd -4、それより大きければ -9を選ぶ。木とtarの大きさの違いがあるため境界は選択の目安。実圧縮サイズは独立に制限する。`compact` は保存量優先の -9固定。-4が3.5 GiBを超えた場合だけ、再梱包・検証が同じ30分枠に収まるとき1回だけ-9で再試行する。封印・転送の15分を確保し、不成立なら最後の検証済み親を保つ。受取側はzstdの圧縮レベルを推測せず実バイトとSHAを検証する。旧gzip親にも既存の復元経路を使う。
* APK依存のAndroid工程には実行時だけ生じる副出力がある。固定したハンドラー、GNでの出力所有、今回のSiso成功記録、同じ実行のNinja記録および全バイトを照合し、別VMで再計画する。次回も拒否した場合は計算ジョブの `BARE_FRONTIER_REJECTION` と区間の停止通知から調べる。
* 新しいVMは固定ソースを直接同期する。検証済みの同じソース・ツールが既に手元にある場合だけ再利用する。独立したビルダーイメージ、2台への常時分散、鍵を恒久的に預ける完全後起動は採用しない。

## GitHubで比較する時点と入口

成果担当が第28回の完了と、既存回収にGitHub資源を使う残作業がないことを台帳で確かめてから、試験枝のリモートHEADをクリーンにチェックアウトする。新しい予約や監視は不要。入口は既にデフォルト枝にある `bare-disk-probe.yml`（workflow ID 411691930）の `workflow_dispatch`。ここで呼ばれる3種類の試験は `workflow_call` 専用で、本番APKも本人の鍵も使わない。

| 試験 | 標準を変えるかを決める条件 |
|---|---|
| `source-v8`、必要なら `source-chromium` | 単独V8の2回再利用で中継に使える余裕は局所4.47秒。V8だけの常設送信役は見送る。複数区間へ同一入力を渡す提案がある時は、直接gclient同期と、初回作成・転送・展開・検証・待ちを含めた合計を比較する。ChromiumモードはsuperprojectのGitが対象で、別途取得するCIPD・Android依存を含まない。[詳しい合否](next_build/trials/source-reuse.md) |
| `split` | libyuv＋ICU 147工程の同じ出力・依存を照合し、受取側の再コンパイル0件、後続アーカイブ一致、再実行0を要求する。2台を割り当てる待ち、追加入力、2台間の中継を含めても1台より短いかを判定する。小さな対象だけでは全APKの並列度を変えない。[計測方法](preflight28/next_split/README.md) |
| `receiver` | 短い先行発券と計算VM生存中の鍵交換を同時起動と比較する。試験鍵での受領・再取得、早期完成時の待ち、追加ジョブを含むVM占有を計測する。局所の20秒対照を本番の35分短縮とはみなさない。効果が見えた時に既存の非公開経路・対象サイズで締切と回復を照合する。[計測方法](preflight28/next_receiver/README.md) |

担当が下記を試験ごとに使う。最初のコマンドは照会だけで、別runが存在する時はdispatch前に停止する。二つ目は試験を実際に行う時だけ使う。既存の認証経路から同じ入力で手動受付を使うこともできる。応答喪失時は同一SHA・試験名で既発行runを照合する。他の本番が新しく必要になった場合は本番を優先し、照合と起動の間の予約競合を考慮する。

```bash
python3 next_build/trials.py split
python3 next_build/trials.py split --recovery-clear --dispatch
```

無料標準の公開Bareリポジトリ・通常のUbuntuホストに限定する。試験ごとの保持は1日。容量は下見時の実占有＋当該試験分、試験用総上限6 GiB、既存リポジトリ設定があればその値のうち最も小さいものを使う。6 GiBは診断の技術上限で、試験時の無料条件とサービス側の空きは当日に別々に判定する。送信前にも容量・期限・他runを再確認する。実地試験は優先順に一件ずつ行い、他の試験のために本番保存を止めない。[GitHubの無料条件](https://docs.github.com/en/actions/concepts/billing-and-usage)
