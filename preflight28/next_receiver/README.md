# Bare checkpoint receiver timing, hosted diagnostic

Select the receiver comparison in the existing **Bare runner disk probe** manual diagnostic entry on the frozen Bare test branch. The reusable workflow has no dispatch, timer, dispatch token, new environment or secret. The parent admits one initial owner run on the exact diagnostic revision after a whole-repository free-space/overlap check. The operator is the Bare build owner. Confirm the existing production run and its pending collection are both clear of the interval. Reserve 6 MiB of free Artifact storage for one day, at most two standard ubuntu-24.04 VMs simultaneously. Repository contents and Actions permissions are read-only. Eight immutable Artifact names are bounded (two tickets, two public certs, two ciphertexts, two receipts). Immediately before each upload the sender rejects extra/symlinked members, sizes the actual files plus ZIP overhead, verifies the public runner, inventories all active workflows and retained Artifacts, and rechecks both the unexpired storage limit and the 2 MiB simultaneous control reserve. Only the fixture and public records reach the diagnostic run's Artifact storage.

The experiment compares the current simultaneous receiver/producer start against an issuer, producer and genuinely later *job start*. In the delayed arm, the ticket job emits the same fixture authorization early, then holds its VM for a controlled 20 seconds before the hosted service can schedule the receiver. Include this entire extra VM in the comparison. The hold is part of the experiment. It does not establish a free timer or displace a real production slot. Do not add this hold or an empty timer VM to the build.

Both arms use the same archive of tracked Bare input at the exact candidate SHA (current workflow and fixed transfer implementation, at most 1 MiB) and the same real CMS framing. A fresh key stays in each receiver's local private directory. The producer reconstructs the public input after receiving the exact ticket. It can finish before a cert is available. It polls only for the named peer of this run/attempt/SHA with a bound of 180 seconds per rendezvous, transfers actual authenticated ciphertext through the regular GitHub Artifact service, and refuses inapplicable/over-limit inputs. The receiver independently reconstructs the input and checks the verified SHA. A final third job reads both receipts by the immutable IDs output by the two receivers, after both have exited. The result and actual job IDs/occupancy are printed in that job's summary. The test captures an early-ready payload in both cases, so the time spent waiting for a late key is observable. This diagnostic produces no APK, touches no upstream parent or Draft and never uses an owner's signing key. Prior production private-parent authorization cannot be inferred from a successful public fixture ticket.

## Acceptance

1. Both cert bindings, reconstructed input SHA, decoded SHA, readbacks and single physical receipt per arm match the original attempt/checkout/mode. The workflow must finish its bounded job windows. A missing/ambiguous/expired peer, wait timeout, or different-generation certificate/receipt stops the arm; no automatic recompile or fallback to a different run.
2. The GitHub started_at of the delayed receiver must actually follow its producer. The measured min(producer_start + 290min, receiver_start + 255min) yields the normal production stop point. Compare **differences** between arms; positive extra budget only benefits deadline-bound intervals. The upper bound is 35 min. The short experiment cannot measure a real 35-minute offset.
3. Record total time, time the producer is ready but waiting for a certificate, VM-seconds (including the issuer), received bytes, run/attempt/IDs, and storage retention. For an early-out fraction f and observed positive budget gain g and additional early wait w, the simplified benefit is (1-f)g − f·max(0,w). The reported break-even f is g/(g+max(0,w)); host/network latency, quota and new issuer maintenance must still be considered. It is a sensitivity estimate. A successful handshake alone is insufficient to switch.
4. Keep simultaneous receipt as the normal build setting. If the hosted comparison shows a worthwhile positive gain for representative long intervals, test the existing private-parent authorization at the same trusted sender permissions and scale with a replaceable nonproduction parent. This public fixture does not test release/Draft isolation, full-size transfer rates or the ability to recover lost private decryption state. In particular, a ciphertext without the corresponding receiver key and a verified receipt cannot be called recovered. If later using a naturally available preparation job in place of the staged 20 s hold, compare its actual occupancy and upper bound first; a new timer/privilege is a separate decision.

For a lost response after success, the Bare owner reads the original compare job or its two **existing** bare-next-rx-<run>-a1-{baseline,delayed}-receipt Artifacts, matched to the exact original job IDs, SHA and attempt. If needed within the one-day retention, the owner can download each to a separate directory with "gh run download RUN_ID -R Areal-U/bare-runner-disk-probe -n NAME -D DIRECTORY", inspect the binding and compare SHA there without a new run. Pre-receipt loss is a diagnostic failure. There is no key escrow or automatic reencryption/retry.

Run isolated regression checks from the fixed repository checkout with "python3 -m unittest discover -s preflight28/next_receiver -p 'test*.py' -v". Python 3.11+ and OpenSSL 3 are required. Tests execute the role commands with independent filesystems and both real frame round trips, remove the original roles and replay the read-only report; they also exercise missing/wrong/oversized peers and a second-attempt rejection. The job clocks in the local regression are explicitly fixtures.
