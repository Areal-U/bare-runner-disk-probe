# Bounded Bare diagnostic admission

The normal command is `python3 next_build/trials.py MODE --recovery-clear`. It prints a manual dispatch payload. Only the existing Bare operator uses the dispatch after checking the current independent recovery registration. Trial runs and writes require an owner-bound first attempt on the reviewed test SHA. Each held Artifact needs separate admission just before upload.

Pre-dispatch and pre-upload inspect all five active states. In the normal case the diagnostic accepts a single complete sweep. Every filter must return the advertised number of rows, zero or just the current job's run ID, with its actual matching status. If a different run appears, a count is missing, or a status differs, the procedure logs up to five numeric IDs and statuses per suspect filter, uses no-cache requests, changes the small page size on each sweep and permits no dispatch/upload until *two* complete clean sweeps. Limited to four sweeps (delays 0/2/5/9 s, 65 s deadline and 6 s per status request). A settling failure is a refusal. The failure of run 45585907929 did not log the conflicting array, so its historical cause remains unclassified. This change is active only for these Bare diagnostics. Normal production keeps its original fail-fast admission.

## Pre-dispatch authenticated capture

If the direct pre-dispatch client has no API credential or has exhausted its anonymous reads, the Bare operator may capture authenticated GET responses. Capture all of them inside **one 120-second window** and execute the command promptly. This mode admits only the read-only standard runner admission job. It cannot estimate occupied bytes, waive an overlap, supply a new permission or replace the live storage checks. Check the physical run from the original payload SHA and marker after a dispatch response is lost. Re-obtain the entire capture if any response was incomplete or the timestamp is old.

`python3 next_build/trials.py MODE --connector-capture capture.json --recovery-clear` validates the short-lived bundle and prints the matching payload. The separate `--dispatch` switch requires an authorized local gh client. The operator can instead use the exact printed payload with the existing registered manual entry. Do not pass an offline capture to the hosted admission job. That job obtains its own checkout SHA, reads the actual registered workflow state and total repository Artifact inventory twice, verifies the expiry and reduces the supplied ceiling to the live occupied bytes plus the bounded incoming trial and concurrent reserve. No data Artifact can be published beforehand.

The capture is JSON with these keys. Timestamps are integer UTC Unix seconds. Each `responses` key is the exact API pathname including its query. The value is the decoded response body. Retain the original service data locally and do not include tokens or signed download URLs.

- `schema` = `bare-next-preflight-reads-v1`; `started_at`, `finished_at`; `workflow_id` = 411691930; `head` = reviewed commit SHA; `mode` = the chosen exact diagnostic name; `responses` is an object.
- BASE = `/repos/Areal-U/bare-runner-disk-probe`. Use the repository response at BASE, and the tested branch endpoint `BASE/git/ref/heads/bare-next-build-prep-20261125` with its full ref, type and SHA.
- `BASE/contents/.github/workflows/bare-disk-probe.yml?ref=main` contains raw content metadata, the base64 file and its blob SHA from the current default branch. The historical registered workflow ID, presence on the default branch, correct test ref and the live in-job status check bind the actual entry.
- `BASE/actions/runs?head_sha=HEAD&event=workflow_dispatch&per_page=100` contains the entire workflow_runs list and total_count, including id, event, workflow_id, head_sha and display_title for each row. Substitute the actual SHA. A previous marker of this mode at this revision blocks another dispatch.
- Read `BASE/actions/runs?status=STATE&per_page=2` once for each state in in_progress, queued, waiting, pending, requested, retaining total_count and workflow_runs with their IDs and statuses. A frozen capture must already be clear in all five responses. A suspect view must be reacquired live; repeating the same capture cannot clear it.

An offline capture is a trusted operator observation, not a signed service attestation. It is not accepted as an input to a hosted write. The limited request uses the smaller of the public diagnostic ceiling (6 GiB) and any available stricter repo configuration. The live job must then shrink it to the observed current requirement or stop.
